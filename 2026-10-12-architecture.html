Architecture field guide · 12 October 2026

One instant.
Two ways to build a UI.

Time Zone Converter separates the question “What time is it there?” from the question “How should the controls work?” That boundary lets you explore two GPUI libraries without writing the conversion logic twice.

A guide to the current starter, not a pull request diff. No server. No shared process. Two native apps, one reusable Rust core.

01 / BACKGROUND

Start with the boundaries

The project started as an empty folder. The useful “existing system” is now a small Rust core and two native desktop frontends. There is no database, web backend, or global state service behind the window. The frontend owns a Timeline value and uses it to render every city.

New to Rust or GPUI? Read the foundations; otherwise skip ahead.

A crate is a unit of Rust code

A Cargo.toml manifest defines a package and its dependencies. Here, time-core provides a library; timezone-component and timezone-base provide executable programs. A Cargo workspace groups packages so commands can build or test them together. It does not mean those packages run in the same process.

GPUI builds native windows, not web pages

Both frontends implement the Render trait. Their render method describes a tree of elements using builders such as div().flex().child(...). The syntax resembles web layout, but GPUI performs native layout, input handling, and GPU rendering. There is no browser DOM in either Rust app. This HTML guide is a separate document.

An entity gives mutable UI state an identity

GPUI manages views and state through entities. An Entity<SliderState> is a handle, not a copied slider. A Context<Converter> lets a handler update the converter and call cx.notify(). Notification tells GPUI that the view has changed and should render again; changing a field alone is not that signal.

A time zone is a rule set, not a number

America/New_York describes historical and seasonal rules. -05:00 is only an offset at a particular instant. An IANA zone allows the library to determine when that offset becomes -04:00. chrono provides date/time values and arithmetic; chrono-tz supplies bundled IANA rules; iana-time-zone detects the Mac's zone name.

The application has three layers

Base GPUI is not “bare GPUI.”

GPUI is the underlying framework in both apps. Base GPUI is a headless component library built on top of it. You already use bare GPUI layout, entities, and render callbacks in each frontend.

Why not put both libraries in one window?

The pinned versions use different GPUI dependency sources. The Component app uses the published gpui 0.2.2; Base uses a specific Git revision of Zed's GPUI and its platform crate. A matching version label is not proof of matching APIs or interchangeable types. A window or entity from one dependency is not automatically valid for the other.

02 / INTUITION

Move the instant, not six clocks

Imagine a meeting scheduled for 2026-10-12 at 23:30 UTC. In Sao Paulo it is 20:30 on Monday; in Tokyo it is 08:30 on Tuesday. Those are not two events. They are two local descriptions of the same event.

The reference zone is another projection. Changing it does not move the meeting. It changes the prominent reference display and the meaning of the row labels “same day,” “+1 day,” and “-1 day.” Those labels compare calendar dates, not elapsed 24-hour periods.

Try the model

This miniature browser demonstration uses a fixed anchor so the examples are repeatable. Choose a reference, then move the slider. Notice that the UTC value stays unchanged when only the reference changes.

The spring gap and the autumn overlap

On 8 March 2026, New York goes from 01:30 EST at 06:30Z to 03:30 EDT at 07:30Z. An elapsed hour skips 02:30. On 1 November, 05:30Z and 06:30Z both display 01:30, but one is EDT (-04:00) and the other EST (-05:00). UTC keeps them distinct.

This model avoids having to decide what an ambiguous local time means. That decision will become necessary if the app later accepts typed local dates and times. It is not a problem the starter silently solves today.

03 / CODE

Follow one gesture through the code

The fastest way to understand the implementation is to follow a slider gesture: the widget proposes a minute offset, the frontend updates the core, GPUI gets notified, and the view formats every city from the new instant.

1. The core stores only the facts it needs

// crates/time-core/src/lib.rs
pub struct Timeline {
    anchor: DateTime<Utc>,
    offset_minutes: i32,
    pub reference: Tz,
    pub zone_detection: String,
}

pub fn instant(&self) -> DateTime<Utc> {
    self.anchor + Duration::minutes(i64::from(self.offset_minutes))
}

pub fn set_offset(&mut self, minutes: i32) {
    self.offset_minutes = minutes.clamp(MIN_OFFSET, MAX_OFFSET);
}

anchor is rounded down to the minute. The offset is bounded to -1440 through +1440 minutes. Local times are derived when needed; they are not separately stored and kept in sync. The six entries in CITIES pair labels with typed chrono_tz::Tz values.

Timeline::now() detects the OS zone, parses it, and records a human-readable detection message. Failure is explicit: the message reports UTC fallback, and the error is printed. reset_now() replaces the anchor and zeroes the offset while preserving the chosen reference.

2. The styled frontend listens to a slider entity

// apps/component/src/main.rs: Converter::new
let subscription = cx.subscribe(&slider, |this, _, event, cx| {
    let SliderEvent::Change(value) = event;
    this.timeline.set_offset(value.start().round() as i32);
    cx.notify();
});

The Component Converter owns three things: its timeline, a handle to SliderState, and the subscription. The slider library manages its own value; the subscription mirrors that value into the timeline. Keeping the Subscription in _subscription keeps the listener alive. The underscore does not make the field disposable.

Now must update both state holders.

The Component handler calls timeline.reset_now() and slider.set_value(0.0, ...). Updating only the timeline would leave the thumb showing an old value even though the city rows had reset.

3. The headless frontend passes a controlled value

// apps/base/src/main.rs: Render for Converter
SliderRoot::new()
    .value(SliderValues::Single(f64::from(
        self.timeline.offset_minutes(),
    )))
    .on_value_change(move |values, _, _, cx| {
        let SliderValues::Single(value) = values else {
            panic!("Single-thumb time slider emitted a range");
        };
        entity.update(cx, |this, cx| {
            this.timeline.set_offset(value.round() as i32);
            cx.notify();
        });
    })

In the Base frontend, the application does not store a separate Entity<SliderState>. It passes the timeline's value to SliderRoot each render. The callback writes proposed changes back to that same timeline. The library still manages interaction details internally; “controlled” means the application supplies the authoritative value.

The Base slider is composed from SliderControl, SliderTrack, SliderIndicator, and SliderThumb. Their dimensions and colors are declared locally. ButtonRoot::style_with_state similarly lets the app style a focused button. In the Component version, ready-made Button and Slider widgets provide those details.

4. Notification connects state to presentation

  1. Input reaches a library widget.A drag or track click yields a proposed numeric minute offset.
  2. The handler changes the Timeline.Values are rounded to integer minutes and clamped by the core.
  3. The handler calls cx.notify().GPUI knows the owning view needs to render again.
  4. Render derives all six rows.display(zone) formats the shared instant; day_difference(zone) compares that city's date to the reference date.

The rendering path does no disk or network I/O. It formats a fixed six-city collection. There is no timer or background queue advancing the timeline. This is a bounded planning tool, not a live clock.

The UI layout is intentionally duplicated. A common GPUI view abstraction would cross incompatible types and hide the very differences this starter is meant to teach. Shared domain logic is valuable here; shared widget code is not yet a requirement.

Run and verify the two boundaries

cd ~/Documents/GitHub/timezone-converter

# The default workspace contains the core and Component app.
cargo run --locked -p timezone-component
cargo test --workspace --locked

# Base has a separate dependency graph and test command.
cargo run --locked --manifest-path apps/base/Cargo.toml
cargo test --locked --manifest-path apps/base/Cargo.toml

The core has five tests for rollover, DST gaps, repeated hours, reference changes, and minute/range boundaries. Each frontend also has a GPUI interaction test that clicks at roughly three-quarter slider width, then drags toward one-quarter width and checks the timeline offset. That proves widget-to-model wiring, not just standalone date arithmetic. It does not exhaustively test every button, keyboard path, or visual style.

What this architecture does not yet provide

No city search, editable city list, arbitrary date entry, persisted preferences, packaged installer, or synchronization between the two apps. The Mac zone is detected at construction, not watched for subsequent OS changes. Adding many cities would also call for revisiting the fixed, directly rendered row list.
